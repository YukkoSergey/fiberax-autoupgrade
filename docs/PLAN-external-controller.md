# План: гібридний автоапгрейд через qemu-guest-agent

Статус: чернетка для постановки задачі. Автор коду в цьому репозиторії — in-guest демон `vm-guardian`;
цей документ описує, як перенести ту саму поведінку назовні, на бік платформи.

## 1. Навіщо

Зараз демон живе всередині віртуалки і тримає там API-токен з правом запису на весь проєкт клієнта.
Це означає: зламана VM = керування всіма серверами проєкту; встановлення на кожну машину окремо;
демон помирає разом із машиною, коли їй бракує пам'яті.

Мета — послуга платформи «автоапгрейд», де:

- рішення, гроші, зміна ресурсів і листи — у зовнішньому контролері;
- всередині гостя нічого постійно не працює і не зберігається; усе, що треба побачити чи зробити
  в гості, виконується разовими командами через `qemu-guest-agent` (далі QGA);
- поведінка для клієнта та сама, що в `vm-guardian` (див. README);
- листи й тексти в кабінеті — мовою клієнта, а не українською (див. §7).

Поза межами цього плану: Solo/GPU (там лише лист власнику, як і зараз), зменшення ресурсів назад,
LLM-радник для невпізнаного софту.

## 2. Архітектура

```
                    ┌──────────────── контролер (сервіс платформи) ───────────────┐
 кабінет клієнта ──▶│ налаштування VM: рівень згоди, стеля витрат, дозволені дані │
 (opt-in, ліміти)   │ цикл опитування → правила → черга змін → виконавець         │
                    │ стан: історія метрик і розмірів тек, журнал дій             │
                    └──────┬──────────────────────┬──────────────────┬────────────┘
                           │ Proxmox API          │ білінг/прайс     │ пошта
              ┌────────────▼───────────┐          ▼                  ▼
              │ нода Proxmox           │
              │  метрики VM (RRD)      │
              │  resize / config       │
              │  QGA: fsinfo, exec ────┼──▶ гість: разовий probe / act, без демона й токенів
              └────────────────────────┘
```

Контролер без стану в гості: історія розмірів тек, лічильники OOM, антиспам листів — усе в його базі.

## 3. Звідки що береться

| Що | Джерело | Примітка |
|---|---|---|
| CPU, мережа, диск I/O | Proxmox: `status/current`, `rrddata` | агент не потрібен |
| Тиха година | Proxmox `rrddata` за 7 днів | в обхід вікна бекапу VM |
| Заповнення ФС | QGA `get-fsinfo` | used/total по кожній ФС |
| Пам'ять: MemAvailable, PSI, своп | QGA `exec` → probe | метрика пам'яті з гіпервізора непридатна: кеш гостя виглядає як «зайнято» |
| OOM: уся машина чи ліміт контейнера | QGA `exec` → probe (журнал ядра гостя) | |
| Що з'їло диск, логи, кеші, власники тек | QGA `exec` → probe | |
| Чищення, logrotate, `growpart`/`resize2fs` | QGA `exec` → act | лише за згодою клієнта, див. §6 |
| Ціни, поточна вартість VM | білінг платформи | напряму, без публічного API |

## 4. Частина в гості: `probe` і `act`

Постійного процесу в гості немає. Є один файл-скрипт, який контролер доставляє й запускає через QGA.

- **`probe`** — лише читає, друкує JSON: meminfo, PSI, лічильник OOM і розбір журналу ядра, топ процесів,
  розміри тек (`du`), знайдені неротовані логи, теки-кеші за ознаками, інвентар софту
  (контейнери, томи, поди, процеси з відкритими файлами, systemd/cron).
- **`act`** — виконує одну дію з фіксованого набору й друкує JSON з результатом:
  `add-logrotate <файл>`, `clean-caches`, `grow-fs`. Довільних команд від контролера не приймає.

Звідки взяти код: функції `inventory`, `owner_of`, `big_unrotated_logs`, `is_text_log`, `add_logrotate`,
`find_caches`, `clean_caches`, `classify_oom`, `grow_fs`, `du_snapshot` у `vm_guardian.py` уже роблять усе це
і залежать лише від стандартної бібліотеки Python. Їх треба відокремити від циклу демона і дати їм JSON-вихід.
Логіка `growers` (порівняння знімків) переїжджає в контролер, бо історія тепер зберігається там.

Профілі відомого софту (`apps.json`: 26 профілів на 27 образів маркетплейсу, див. `docs/marketplace-images.md`) —
це дані, а не код, тому контролер використовує той самий файл. Назву образу сервера контролер знає напряму,
але розпізнавання за ознаками в гості лишається основним: клієнт міг поставити софт сам або змінити розкладку.
Поле `advice` там зараз українською — у контролері його треба замінити на ключі повідомлень (§7).

Відкрите питання для команди: Python є не в кожному образі. Варіанти — вимагати Python 3 (є в стандартних
Linux-образах), або переписати probe/act на статичний бінарник (Go). Для Windows — окрема реалізація, пізніше.

## 5. Логіка контролера

Правила ті самі, що зараз; пороги — параметри VM зі значеннями за замовчуванням.

| Ресурс | Умова | Дія |
|---|---|---|
| Диск | зайнято ≥ 85% або вільно < 6 ГБ | probe → (за згодою) logrotate, чищення кешів → якщо досі мало і росте дозволене → +крок диска; інакше лист «що і де виросло» |
| Пам'ять | MemAvailable < 10% за 15 хв, або PSI > 10% за 15 хв, або OOM усієї машини | +1 ГБ |
| Пам'ять | OOM через ліміт контейнера | лише лист |
| CPU | > 85% за 30 хв | +1 ядро |

Гроші — як у `vm-guardian setup`: базова ціна VM на момент увімкнення, поріг попередження, жорстка стеля
загальних місячних витрат. Пропозиція стелі за замовчуванням: більше з «5 апгрейдів CPU» і «+30% від
поточної ціни». Понад стелю — стоп, лист, ручне зняття.

Відмінність від in-guest версії, яку варто закласти одразу: **крок диска має залежати від швидкості росту**,
а не бути фіксованим +1 ГБ. На тестовій машині дані росли на 9 ГБ за добу при кроці 1 ГБ за ніч.

## 6. Рівні згоди клієнта

Клієнт вмикає послугу для VM і обирає рівень. Вищий включає нижчі.

1. **Спостереження** — метрики, `get-fsinfo`, `probe`; лише листи.
2. **Автоапгрейд** — плюс зміна ресурсів у межах стелі та `act grow-fs`.
3. **Чищення в гості** — плюс `act add-logrotate` і `act clean-caches`.

Без рівня 3 платформа нічого не змінює у файлах клієнта, крім розширення ФС після збільшення диска.

## 7. Мови

Вимога: кожен лист і кожен текст у кабінеті клієнт отримує своєю мовою.

- Мова — властивість клієнта з профілю кабінету; для послуги її можна перевизначити на рівні VM
  (адресат листів про конкретну машину може бути іншою людиною).
- Якщо перекладу для мови клієнта немає — англійська. Українська не є запасною мовою.
- Жодних готових фраз із гостя: `probe` і `act` повертають лише дані й коди
  (`{"action": "add-logrotate", "path": ..., "freed_bytes": ...}`), текст складає контролер із шаблонів.
  Нинішній `vm_guardian.py` цього не дотримується — українські рядки зашиті в код, тому його повідомлення
  переносити не можна, лише логіку.
- Шаблони листів — окремі файли з ключами повідомлень, по одному набору на мову; додати мову = додати файл,
  без змін у коді. Тема листа теж із шаблону.
- За локаллю клієнта форматуються числа, суми, дати й розміри («7,6 ГБ» / "7.6 GB"). Час тихої години
  й запланованого перезавантаження показувати в часовому поясі клієнта, а не в UTC.
- Не перекладаються: шляхи, назви контейнерів, процесів і пакетів, вивід команд.
- Журнал дій у кабінеті зберігає коди й параметри, а не готовий текст, щоб показувати його поточною мовою.
- Журнали самого контролера для інженерів — англійською.

## 8. Зміна ресурсів

1. Перевірки: VM не заблокована (бекап, міграція, снапшот), агент відповідає, бюджет дозволяє.
2. Диск: `resize` на ходу → `act grow-fs` → перевірка через `get-fsinfo`.
3. Ядра й пам'ять: якщо для VM увімкнено hotplug і гість його підтримує — на ходу; інакше зміна
   лягає в pending і застосовується перезавантаженням у тиху годину.
4. Перевірка після зміни через `probe` (гість бачить нові ресурси); лист власнику з вартістю до і після.
5. Диск назад не зменшується — це треба явно сказати клієнту при увімкненні.

Виклики Proxmox API, які знадобляться (звірити з версією PVE у продакшені):
`GET /cluster/resources`, `GET .../qemu/{vmid}/status/current`, `GET .../rrddata`,
`POST .../agent/ping`, `GET .../agent/get-fsinfo`, `POST .../agent/exec`, `GET .../agent/exec-status`,
`POST .../agent/file-write`, `PUT .../resize`, `PUT|POST .../config`, `POST .../status/reboot`.

## 9. Що може піти не так

| Ситуація | Поведінка |
|---|---|
| Агент не відповідає (немає, завис, VM з власного ISO) | рівень падає до «тільки CPU з гіпервізора»; один лист власнику; диск і пам'ять не чіпаємо наосліп |
| Агент заморожений під час бекапу (`fsfreeze`) | не опитувати у вікні бекапу; таймаут ≠ аварія |
| `exec` завис або повернув сміття | таймаут, одна повторна спроба, далі — як «агент не відповідає» |
| `du` на великому диску довгий | запускати з `nice`/`ionice`, рідко (раз на 6 год і при тривозі), з обмеженням глибини |
| VM мігрувала на іншу ноду | адресувати за `vmid` через `/cluster/resources`, а не за нодою |
| Зміну прийнято, а гість її не бачить | не повторювати; лист інженеру платформи й власнику |
| Контролер упав посеред зміни | черга змін ідемпотентна, стан кроку зберігається до виклику API |
| Клієнт сам змінив ресурси | перечитувати конфігурацію VM перед кожною дією |

## 10. Безпека

- У гості немає токенів і постійного коду. Скрипт probe/act доставляється щоразу або перевіряється за хешем.
- `guest-exec` — це root у гості. Контролер викликає лише probe/act з фіксованими аргументами;
  кожен виклик пишеться в журнал, доступний клієнту.
- Обліковий запис контролера в Proxmox — окремий, з мінімальною роллю (аудит, монітор, агент, зміна
  диска/CPU/пам'яті, керування живленням) і лише на пули клієнтів, що ввімкнули послугу.
  Точні назви привілеїв звірити з версією PVE.
- З гостя назовні йдуть лише метрики, шляхи й назви процесів — не вміст файлів. Шляхи можуть містити
  персональні дані (наприклад, e-mail у назвах тек Nextcloud): у листах і журналах маскувати.

## 11. Етапи

| Етап | Що здаємо | Критерій готовності |
|---|---|---|
| 0. Розвідка | перевірка на стенді: `get-fsinfo`, `exec` з JSON-виходом, hotplug диска/CPU/пам'яті, права ролі | таблиця «що працює на якому образі та версії PVE» |
| 1. Спостерігач | контролер читає метрики й fsinfo, шле листи; нічого не змінює; листи вже із шаблонів, щонайменше двома мовами | на 5–10 власних VM тиждень без хибних тривог; той самий лист приходить мовою клієнта |
| 2. probe | винесений з `vm_guardian.py` probe; історія розмірів у контролері; лист «що і де виросло» | на тестовій VM звіт збігається з `vm-guardian diagnose` |
| 3. Автоапгрейд | бюджет, черга, тиха година, resize + grow-fs, перевірка після зміни | диск, пам'ять і CPU збільшуються на стенді; стеля зупиняє; жодного токена в гості |
| 4. Чищення | `act add-logrotate`, `act clean-caches` за рівнем згоди 3 | тести на підробленому софті: текстовий лог ротується, журнал БД не чіпається |
| 5. Кабінет | увімкнення послуги, рівень згоди, стеля з підказкою, дозволені дані, вибір мови листів, журнал дій | клієнт проходить налаштування без підтримки; усі тексти перекладені всіма мовами кабінету |
| 6. Викочування | власні VM → охочі клієнти → усі стандартні образи | — |

Етапи 1–2 нічого не змінюють у клієнтських машинах і дають користь самі по собі; на них можна зупинитись
і зібрати статистику порогів перед тим, як вмикати гроші.

## 12. Що вирішити до старту

1. Python у гості чи статичний бінарник для probe/act.
2. Чи вмикати hotplug CPU й пам'яті для VM за замовчуванням (впливає на те, чи потрібні перезавантаження).
3. Як рахувати крок диска: фіксований, від швидкості росту, чи «до N днів запасу».
4. Чи є бекапи частиною стелі витрат (зараз так: дорожчання бекапів з'їдає запас).
5. Що робити з VM без агента: пропонувати встановити чи не пропонувати послугу.
6. Windows: у першій версії чи пізніше.
7. Якими мовами запускаємося і хто відповідає за переклади шаблонів.

## 13. Що відомо з in-guest версії

Перевірено на одній VM (Debian 13, Cluster Server):

- у стандартному образі Debian 13 агент уже встановлений і хост ним користується (ping, fsfreeze під час бекапу);
  інші образи не перевірялись;
- діагностика диска, logrotate, розрізнення OOM, перевірка бюджету працюють;
- реальне збільшення ресурсів з перезавантаженням через API на момент написання ще не відбулось ні разу —
  цей шлях треба пройти на стенді першим;
- поріг PSI 10% узято як відправну точку, а не з вимірювань.
